# STACKED run music: auto-play on run start (2026-09-26)

Owner request: the arcade music player must auto-play when a STACKED game
begins, with the starting track randomized.

## Root cause

The parent started STACKED music with `void startArcadeMusicForGame('stacked')`
at the end of `mountStackedSession`, after `await import('./src/stacked-host.mjs')`
(and, for Ranked, after the wallet modal). Its `play()` therefore ran outside the
Free/Ranked click's transient user activation. Default Chromium usually allowed
it through sticky activation; a strict autoplay policy (Safari/iOS, Chromium
`--autoplay-policy=user-gesture-required`) rejected it with `NotAllowedError`
once the chunk import was slow, and the rejection was swallowed. Nothing on the
parent observed the child's `ready -> running` transition, so the run stayed
silent. Hard Money Heroes was unaffected because `beginOfficialLevel` starts its
music synchronously in the click.

The `stacked` queue (the default 26-track queue), the random start
(`chooseArcadeMusicStartIndex`) and the mute/music setting were checked and are
not causes.

## Fix (parent presentation only; nothing in `apps/stacked/**`)

- `blessArcadeMusicElement()` (main.js music helpers): called as the first
  STACKED step of `startOfficialMode`, before any await. A muted `play()` in the
  click unlocks the shared element (WebKit and Chromium keep an element unlocked
  after one user-gesture play), then it is paused and rewound unless a real start
  claimed the element first. Skipped when music is already playing or muted.
- `apps/portal/src/stacked-run-music.mjs`: one state machine per mounted session.
  `mount()` starts a fresh random song (music on) or only follows the queue
  context (music off/muted). The first `running` of a run keeps a song that is
  already playing (switching the queue context) or starts a fresh random one
  (the retry covers a blocked mount start, using the child's Start click
  activation). `terminal` arms the next run for a fresh random song. Pause,
  resume, score ticks and duplicate states never restart the song. `dispose()`
  runs in `destroyStackedSession`.
- A new session never repeats the previous track when the queue has more than
  one song (`chooseArcadeMusicStartIndex` excludes the previous index).

Music never reads or writes the run, seed, input evidence or result.

## Evidence

- `tests/stacked-run-music.test.mjs`: mount, ready/paused-before-start, running,
  paused/resume, terminal and restart, music off, disposal, no-repeat, and the
  main.js wiring (bless before the first await of `startOfficialMode`).
- `npm run smoke:stacked:music` (`scripts/stacked-music-autoplay-smoke.mjs`):
  system Chrome with the default and the strict autoplay policy, the
  stacked-host chunk held back 6 s, two sessions per page. Asserts unmuted
  playback on a STACKED queue track before and after Start, the song kept at run
  start, a different random track for the second session, and no rejected
  audible `play()`. Report: `.tmp/stacked-music-autoplay/report.json`.

## Known follow-ups

- Pausing STACKED does not pause the arcade music (HMH does). Unchanged here.
- Under a strict policy the analyser `AudioContext` (`stacked-audio.mjs`) may stay
  suspended, so the visualizer can fall back to ambient while the music itself
  plays through the element's direct output.
- Ranked was not browser-probed (needs a wallet); it goes through the same
  click-time bless and mount path.
